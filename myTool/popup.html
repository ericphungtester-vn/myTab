Guide

Language: English (default), Tiếng Việt, Español, Français, Deutsch, Italiano, Português, 中文, 日本語, 한국어, Русский, العربية, Ελληνικά, עברית, हिन्दी, ไทย, or classic Lorem Ipsum (Latin) — each uses a themeless bank of common words, not real sentences. Chinese, Japanese, and Thai are joined with no spaces (as normally written); the word counter below the output box counts by whitespace, so it won't be meaningful for generated text in those three — the character counter is still exact for every language. Arabic and Hebrew display right-to-left automatically. Hidden entirely when Unit is Strings, since Strings has nothing to do with any language.

Not every non-Latin script is covered — this list is scoped to ones with word banks I'm confident are accurate (not fabricated). Ask if you want another script added (e.g. Georgian, Armenian, Khmer, Lao, Sinhala, Tibetan, Mongolian, Amharic, Burmese).

Unit — pick one, and "Amount" is measured in that unit (switching units resets Amount to that unit's own default and regenerates immediately):

  • Characters (default Amount 1) — one continuous piece of exactly that many characters, cut from the Language's word bank.
  • Words (default 1) — exactly that many words, raw (no capitalization or trailing punctuation).
  • Sentences (default 1) — that many sentences, each a random 6–14 words with capitalization and punctuation, flowing together as one piece (not one per paragraph).
  • Paragraphs (default 2) — that many separate paragraphs, each built to the "Chars/paragraph" length (including its trailing punctuation mark), joined using "Line break": no blank line, or with a blank line between paragraphs (default).
  • Strings (default 16) — see below.

Strings is unrelated to Language and its word banks — it generates a random string of exactly "Amount" characters from the checked classes: ABC uppercase, abc lowercase, 123 digits, #$& symbols (all 32 standard keyboard symbols), and Space — like a password/random-string generator. Space defaults off; the other 4 default on with every character enabled (95 characters total). Click a class's text label (not its checkbox) to open a picker and enable/disable individual characters within that class — Space has only one character, so it has no picker.

Every checked class is guaranteed at least one character in the result (the rest fill in randomly across all checked classes) — like a real password generator, not a flat character soup. This means Amount must be at least as large as the number of checked classes (e.g. 5 classes checked needs Amount ≥ 5); Generate shows an inline error instead of running if that's not met, or if every class/character is unchecked.

Output box: click Generate to fill it, or paste your own text in — the counters below (characters, words, sentences, paragraphs, lines, spaces) always reflect whatever is currently in the box, whether generated or pasted. Sentences are split on . ! ? (and 。！？। for CJK/Hindi text); paragraphs are blocks separated by a blank line, or if there's no blank line anywhere, each non-empty line counts as one paragraph; spaces counts all whitespace (spaces, tabs, line breaks). Uncheck Count spaces to exclude whitespace from the character count. Click the copy icon in the corner of the box to copy it to the clipboard.

⟲ Reset (next to "Text" in the left sidebar): restores every setting on this tool back to its default (English, Characters, Amount 1, etc.) and regenerates immediately.

Your last-used settings — including which individual characters are enabled per class — are remembered via Chrome Sync.

Generates a real, valid file of the format and size you specify, then downloads it immediately — useful for testing upload limits, storage quotas, or just needing a file of a certain size.

Type: Plain Text, CSV, JSON, HTML, XML, Markdown, and Random Binary have no minimum size. Every other type is a genuine file of that format (a real image/archive/document, not just renamed bytes) — each has a small minimum size, since a valid file of that format can't be smaller than its own header/structure. Generate shows an inline error instead of running if you go below it.

Excel / Word / PowerPoint / EPUB (.xlsx/.docx/.pptx/.epub) are Office Open XML / EPUB files — really just a ZIP of small XML parts — that open correctly in their respective apps (and EPUB readers). The extra size beyond the minimal structure is filler text placed in cell A1 (Excel), the first paragraph (Word), the first slide's text box (PowerPoint), or the first chapter (EPUB) — it's the only thing that changes as you increase the size.

PNG / BMP / GIF / JPEG / TIFF / ICO render a real gradient/pattern image (not a solid color), with pixel dimensions that scale up with the requested size — up to a cap of 256x256, so the image stays clearly visible without needing to zoom (ICO wraps a real PNG, so it scales the same way). SVG draws a real gradient rectangle plus visible filler text, scaling by text length rather than pixel count. Sizes beyond what the image needs are simply extra bytes appended past the image data, which viewers ignore.

Every format shows or plays back something real when opened, not a blank/silent shell: HTML and XML put the filler text where it's actually rendered (not in a comment), PDF draws it as real text on the page, and WAV is an audible 440 Hz tone rather than silence.

Size: enter an amount and pick B / KB / MB. Capped at 50 MB to avoid freezing the popup.

KB/MB means: macOS Finder and Windows Explorer disagree on what "KB"/"MB" means — Finder divides by 1000 (the actual SI definition), Explorer divides by 1024 despite using the same labels. No single file size reads as a clean round number on both, so pick whichever OS you'll be viewing the file's size on; the "actual size" shown after Generate is computed the same way.

Filename: name for the downloaded file — the correct extension is added automatically based on Type.

After Generate & Download, the actual byte size produced is shown below the button — it matches your requested size exactly for every format (once above its minimum).

Synthetic test data only. Every value is randomly generated on the spot and recombined from real name/address data — nothing is ever derived from or matched to an actual person, and nothing here is ever rendered as a visual ID/passport mockup, only plain text fields. This tool exists to test form/validation logic (does your form accept correctly-formatted names, addresses, phone numbers, IDs — does it correctly compute/verify a check digit), not to produce anything resembling a real document or a real person's data.

Pick a Country (21 available) and click Generate — one click fills in two sections: Personal (First/Middle/Last/Full Name, Address Line, Postal Code, Phone Number, every National ID variant that country has — e.g. Spain gets both DNI and NIE, Singapore gets both NRIC and FIN — a Passport Number, and a Passport MRZ) and Company (Company Name, Tax Code, Business Registration Number). Click any field's copy icon to copy just that value, or Generate again for an entirely new profile (a fresh company too, unrelated to the previous one).

Names/Address/Postal Code/Phone use real per-country name lists and phone/postal formats (verified against Faker.js's own locale data, a well-established reference for this kind of test data), randomly recombined — realistic-looking, but not tied to anyone real. Two countries have no dedicated source data: Chile falls back to Spain's Spanish-language names as a reasonable approximation; Bulgaria, Malaysia, and Singapore (no single good-fit source given their scripts/multi-ethnic makeup) use a generic name/street pool instead of fabricating country-specific names. "Middle Name" is synthesized everywhere as a second given name from the same pool, since most of these naming systems don't have a Western-style middle name to begin with. Vietnamese and Chinese names correctly use family-name-first order in Full Name.

National ID — for Italy, Brazil, Chile, Portugal, France, Spain (DNI/NIE), Sweden, Norway, Poland, Bulgaria, Finland, South Africa, China, India, and Singapore (NRIC/FIN), the check digit(s) are computed with that country's real, published checksum algorithm (verified against independent reference implementations) — so the generated number will pass a real checksum validator, even though the person/date/place it encodes is made up. Romania's CNP checksum is included for structural completeness, but the source it was verified against itself flags that algorithm as unconfirmed by an official spec. Vietnam (CCCD), USA (SSN), UK (NINO), Indonesia (NIK), and Malaysia (NRIC) have no published public checksum, so only the field structure/length is real.

Passport Number is a simplified per-country letter/digit pattern (e.g. 2 letters + 7 digits) for testing format validation — passport numbering isn't checksum-verifiable the way national IDs are, and real series vary by document batch, so treat this as "plausible shape," not an authoritative reproduction of any country's actual issuing scheme.

Passport MRZ builds the standard ICAO 9303 TD3 machine-readable zone (the 2 lines of 44 characters at the bottom of every passport's photo page), with correctly computed check digits (document number, birth date, expiry date, and the final composite check) using the universal algorithm every country's passports share, and reuses the same generated name as the rest of the profile — transliterated down to plain A-Z the way real MRZs are (diacritics stripped, spaces become "<"). China's name is in Chinese characters, which can't be mechanically transliterated to the Pinyin a real Chinese passport would use, so its MRZ uses a generic Latin placeholder name instead.

Company — Tax Code and Business Registration Number are checksum-verified for most countries (Brazil, Bulgaria, China, Finland, France, India, Indonesia, Italy, Norway, Poland, Portugal, Romania, South Africa, Spain, Sweden, Vietnam, Singapore — verified against independent reference implementations), while the UK's Tax Code (a real UTR) is checksummed but its Business Registration Number is a structural placeholder (no public Companies House-number checksum exists), and the USA's EIN and Malaysia's Tax Code/registration numbers are format-only (no public checksum for either). Several countries genuinely use one unified number for both fields (e.g. Brazil's CNPJ, the USA's EIN) rather than that being a shortcut — that's how those countries' real systems work. France's Tax Code (VAT) is mathematically derived from its Business Registration Number (SIREN), matching the real relationship between the two. Chile reuses the same RUT system as its personal ID (real-world Chilean RUTs cover both people and companies). Company Name is a random surname/word plus a real local legal-entity suffix (Ltda., Sp. z o.o., Pte Ltd, etc.) — not a real registered business.

Resizes and/or compresses an image entirely in your browser — the image is read from the file you pick and written back as a download; it never leaves your machine and no permissions are used. Drop an image onto the box (or click browse); it shows the original name, dimensions, and size, and auto-fills the width and height from the original. EXIF orientation from phone photos is applied automatically.

Everything is in one form — set any combination and click Resize:

  • Width / Height (px) — pre-filled from the original. Lock ratio (on by default) keeps the aspect ratio: edit either one and the other follows.
  • File size — optional. Leave it blank to just resize. If you enter a target (KB/MB, base 1000), the tool binary-searches the encoder quality to land at or under it. The width/height above act as a maximum — if even the lowest quality can't reach the target at those dimensions, it downscales further and reports the final size. A file-size target needs a lossy format (JPEG or WebP); with PNG/Original it will ask you to switch.
  • Format — Original, JPEG, PNG, or WebP.

Click Resize & Download to save the result (named <original>-resized.<ext>) and show a preview; the result line shows the final dimensions, size, and (for lossy) quality. Nothing is stored between sessions — it's a one-shot transform.

Compares two texts and shows the differences side by side — original on the left, changed on the right, with line numbers. Paste into both boxes and click Compare.

Matching uses a line-level diff (like git diff): unchanged lines line up, added lines are green on the right, removed lines are red on the left, and a changed line is paired left/right with the exact words that differ highlighted within it. The summary line reports how many lines were added / removed / changed and an overall similarity %.

Options: Ignore case (treat A and a as equal), Ignore whitespace (collapse runs of spaces/tabs and ignore leading/trailing), and Trim lines (ignore only leading/trailing spaces). These affect matching only — the text shown is always your original.

Download HTML report saves the full side-by-side diff as a self-contained text-comparison.html file you can open in any browser — handy when the comparison is wider or longer than the popup. Each side is limited to 2000 lines. Nothing is stored between sessions.

Synthetic test data only. Every value is randomly generated on the spot. Bank and branch codes are random — they are not mapped to any real institution, and no output corresponds to a real account. This tool exists to test form/validation logic (does your form accept a correctly-formatted IBAN, does it verify the checksum), not to reproduce any real bank or account.

Pick a Country (35 SEPA+ countries available) and click Generate — you get an IBAN (plus a space-grouped copy for readability), a SWIFT / BIC, the Bank Code, a Branch Code where that country uses one, and the Account Number. All fields are consistent — the Bank Code and Account Number are the actual segments inside the IBAN above them. Click any field's copy icon to copy just that value, or Generate again for a new set.

IBAN is built to the official ISO 13616 structure for each country (correct total length and bank/branch/account layout) and carries correct ISO 7064 MOD-97-10 check digits — so it passes the universal IBAN checksum that virtually all validators and payment libraries use. Some countries additionally embed a national check digit inside the account portion (e.g. France's RIB key, Belgium's mod-97, Italy's CIN, Spain's DC); those national digits are not separately computed here (they're random), so a strict national-level validator may reject them even though the IBAN checksum itself is valid.

SWIFT / BIC follows the ISO 9362 format (4-letter bank code + 2-letter country code + 2-character location code, plus an optional 3-character branch code — 8 or 11 characters). There is no BIC checksum, so this is format-correct only. Account Number is the domestic account segment of the IBAN; most countries have no universal standalone account-number checksum, so treat it as correctly-shaped, not independently checksummed.

Synthetic test data only. For the ~150 countries that don't use IBAN, there's no international standard for account structure the way IBAN defines one — so this tool covers a curated set of 18 major countries whose domestic bank formats are publicly documented, rather than fabricating structures for countries where no reliable format exists. Everything is randomly generated; bank/branch codes are not mapped to any real institution.

Pick a Country and click Generate. You get that country's real domestic identifiers — e.g. USA's ABA routing number, Australia's BSB, Canada's institution + transit, India's IFSC, Japan's bank + branch code, Mexico's CLABE, Argentina's CBU — plus an Account Number and a SWIFT / BIC (ISO 9362, correct format). Click any field's copy icon to copy just that value.

Checksums: three of these identifiers carry a real, verifiable check digit, computed with the published algorithm and verified in the test suite against known reference values — the USA ABA routing number (weighted MOD-10), Mexico CLABE (MOD-10), and Argentina CBU (two check digits). All other identifiers and account numbers have no public checksum standard, so they are correct in format/length only — plausible shape for testing, not independently checksummed.

Synthetic test data only. The BBAN (Basic Bank Account Number) is the domestic part of an IBAN — the account number a country used before IBAN. Some countries embed a national check digit inside it (e.g. France's RIB key, Italy's CIN). The IBAN tab only guarantees the outer mod-97 IBAN checksum, leaving those national digits random; this tab computes them correctly, so the account number is valid at the national layer too — and the assembled IBAN is valid at both layers.

Pick a Country and click Generate. You get the domestic pieces (bank / branch / account), the national check digit shown as its own field, the full BBAN, and the assembled IBAN (valid at both layers). Bank/branch codes are random and not mapped to any real institution.

Coverage is deliberately limited to 10 countries whose national check-digit algorithm was verified against a real ISO 13616 registry IBAN (the algorithm reproduces the check digit embedded in a known-valid IBAN): Belgium, Finland, France, Italy, Monaco, Norway, Portugal, San Marino, Slovenia, Spain. Countries whose algorithm couldn't be verified unambiguously (e.g. Estonia, whose single reference was inconclusive) are deliberately left out rather than guessed — for those, use the IBAN tab (valid at the mod-97 layer).

Synthetic test data only. Generates fake payment-card details for testing checkout/validation forms. Card numbers are randomly generated with a valid Luhn check digit and the correct network prefix and length — so they pass a real card-number validator — but they belong to no real account and cannot be used for any transaction. The prefix identifies the card network (Visa, Mastercard, …), not any specific bank.

Pick a Network — Random (default), Visa, Mastercard, American Express, Discover, JCB, Diners Club, or UnionPay — and click Generate. You get the Card Number (grouped for readability; its copy button copies the raw digits), the Network, the security code (CVV / CVC / CID / CVN depending on network — 4 digits for Amex, 3 otherwise), an Expiry (MM/YY, always a future date), and a Cardholder Name. Generate again for a fresh card.

Numbers use each network's real IIN ranges (Visa 4…, Mastercard 51–55 / 2221–2720, Amex 34/37, etc.) and standard lengths (15 for Amex, 14 for Diners, 16 otherwise) — enough to satisfy format + Luhn checks. The Luhn algorithm is the same one verified in the Profile tool's tests.
